# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A full-stack take-home for STR Mission Applications, specified in `REQUIREMENTS.md`. The task is to build a working "first cut" that an engineer would demo to a prospective user, Maverick, a Navy pilot who runs a detachment. There's no spec, only his discovery-call notes (Appendix A of `REQUIREMENTS.md`). In the review, the author demos the app as if to Maverick and then defends every call made, so the code has to be something they can explain and stand behind.

**The customer's problem.** His tasks are spread across sticky notes, email flags, a whiteboard and his memory. He wants one place for everything. But he shuts any app that shows him the whole pile. He hates notifications, yet things that go quiet burn him: he missed a maintenance sign-off. He asks for a pilot's "scan": always knowing what's now and what's next. Rhythm items (Monday brief, Friday roll-up, quarterly currency paperwork) get re-entered by hand every time. Squadron and delegation features are "someday", not day one. He doesn't care about looks; he wants to feel ahead of the jet.

Every feature should trace back to one of these tensions:
- Everything in one place, but he can't look at everything. So the app opens on Today, and the full list is one click away.
- He hates pings but gets burned by silence. So alerts stay in the app, and snooze quiets an alert but never hides the task.
- Re-entering rhythm items by hand. Clone is the first answer to that.

The design decisions and the reasoning behind them are in `DECISIONS.md`.

**Hard constraints from the brief:**
- `docker compose up` on a machine with only Docker must start everything, app and database. It runs locally only: no deploying, no cloud services, no external APIs.
- The time box is 3–4 hours. Prefer cutting scope to half-building a feature. Items 1–7 in the README's priority list come before the "if time allows" items.
- `PREBRIEF.md` must be **human-written**. Don't write or rewrite its prose. At most, point out facts the author may want to add.
- `DECISIONS.md` is a running log kept *during* the build, not reconstructed at the end. Reviewers read it first. When a real choice gets made (something considered, chosen and why), add an entry under a new `##` section at the bottom (bold lead-in, then a few plain sentences, matching the existing entries), or suggest the entry so the author can write it. Don't backfill or polish earlier entries.
- `README.md` must keep the one command to run the app.

Progress is tracked in `PLAN.md` (parts of planned work, not strict commits); keep it accurate as work changes. Built so far: the models and seed, the JSON API (`/api/me`, `/api/tasks` list/create/update), the scan screen, the All tasks tab (full table with search, filters, sort and pages), the task detail and edit dialog (`components/dialog/TaskDialog`, rules in `helpers/taskForm.ts`), and new task and clone (the same dialog in `new` and `clone` modes, `planCreate`), with the New icon, section and filter, collapsible scan sections and a creation toast, and alerts and snooze (status icons, the bell's snooze menu, End snooze in the dialog, Alerting and Snoozed filters), and "You're caught up" and printing a scan section as an index card.

## Commands

Reviewers use the Docker path, so it's the one that must keep working. After changing dependencies, check it with `docker compose up --build`.

```bash
docker compose up --build          # full app at http://localhost:8000
docker compose down -v --rmi local # wipe the DB and the built app image: next start rebuilds and re-seeds (the reviewer's first run)

# Local dev with hot reload (three terminals)
docker compose -f docker-compose.yml -f docker-compose.dev.yml up db   # Postgres on :5432
cd api && source .venv/bin/activate && fastapi dev main.py             # API on :8000, docs at /docs
cd web && npm run dev                                                  # UI on :5173, proxies /api -> :8000

# Web checks (run from web/)
npm test                           # vitest run (jsdom, globals, setup in src/test-setup.ts)
npx vitest run src/path/to.test.ts # single file
npx vitest run -t "name"           # single test by name
npm run lint                       # oxlint (not ESLint)
npm run build                      # tsc -b + vite build; this is the type-check
npm run format                     # prettier on src (single quotes, no semicolons: web/.prettierrc.json; web only)
```

There are no API tests. That was deliberate: UI tests target derived status and date logic.

## Architecture

- **Two containers.** `db` (Postgres 17) and `app`. The Dockerfile builds the React app in stage 1 and copies `web/dist` into `api/static`. FastAPI mounts that at `/` after all routes. All API routes must live under `/api/*` and be registered **before** the static mount at the bottom of `main.py`. There is no CORS and no proxy in production. In dev, Vite proxies `/api`.
- **No migration tool.** `SQLModel.metadata.create_all` runs in the FastAPI lifespan. Table classes must be imported before it runs.
- **`schema.sql` is the reference schema, not what runs.** `create_all` won't create its CHECK constraints or partial index unless the SQLModel models declare them (for example with `__table_args__`). Keep the models and `schema.sql` in sync. The database uses snake_case columns, and the JSON API uses camelCase (`remindAt`, `ownerId`, `snoozedUntil`, ...).
- **Seeding.** On startup, if `tasks` is empty, insert `api/seed/users.seed.json`, then `tasks.seed.json`, via `api/seed/materialize_seed.py`. The seed stores *day offsets*, not dates. They're resolved against "today" in `DEMO_TZ` (default `America/New_York`), because the container clock is UTC. Never put fixed dates in the seed. The seed must also pass the schema checks. Default local times when the seed gives only a day: deadline 20:00 (Eastern 20:00 = Pacific 17:00, and an evening demo isn't all red), reminder and snooze 07:00. Changing the seed needs `docker compose down -v` to re-seed.
- **Frontend.** React 19 + TypeScript + Vite, TanStack Query for server state, TanStack Table **v9** for sorting, filtering, search and pagination (all "if time allows" items). Table v9's API differs from most v8 examples. Styling is Tailwind v4 (Vite plugin) and dates use date-fns. The plan says no router, no state store and no form library: use `useState` for the active tab (Today / All) and the open task. The client loads all tasks, archived ones included, in one request.
- **Web code layout.** `src/api/client.ts` holds the fetch calls (ISO strings become `Date`s only here); `src/types.ts` at the top; `src/useNow.ts` (clock hook) at the top too; `src/helpers/` holds plain functions with no React, and their tests (`taskHelpers.ts`, `formatDates.ts`, `taskForm.ts`, `snooze.ts`, `printCard.ts`); `src/components/` holds the UI pieces, grouped in folders: `scan/` (`TaskSection`, `TaskLine`: one task in a scan section, not a table row; `TodayClear`: what an empty Today says; `PrintCard`: a section as index cards, print only), `table/` (`TaskTable`, `TaskTableToolbar`), `dialog/` (`TaskDialog`, its parts `TaskFacts` (`TaskState`: one short line under the heading, "Overdue by 12 days", "Snoozed until Fri 07:00 · overdue by …  End snooze", the snoozed alert's words still red or amber, End snooze outlined blue like Clone, or nothing; `TaskDates`: "Created …" in small print above the buttons), `DateTimeField`, `Select`, `Checkbox`, `FieldError`, and `styles.ts`), `shared/` (`Tag`, `TitleButton`, `Toasts`, `Icons` (status, New and time icons), `SnoozeMenu`). Tests sit next to the file they test. Keep things that are used together, together.
- **Single user.** There's no auth. The API acts as the one seeded user (id 1). Display name is `preferredName` if set, otherwise first + last name.

## Domain rules (easy to get wrong)

- **Completed and Overdue are derived, never stored.** Completed means `completedAt` is set. Overdue means the deadline has passed and the task isn't completed. Stored `status` is only `Not started` | `In progress` (the same words the UI shows, so there is no mapping). Un-completing a task restores its prior status.
- **Timestamps are UTC in storage, shown in local time.** "Today" and "Tomorrow" are the *viewer's* local day, computed in the UI. A task is overdue the minute its deadline passes.
- **Alerts are in-app only; nothing buzzes.** A task alerts when its deadline has already passed (overdue), its `remindAt` has been reached, or (due soon) its deadline is within the next 24 hours and it has **no reminder**: his reminder wins, so due soon never fires before it. First match wins: overdue, reminder, soon (`alertReason`; `alertState` is the same but `null` while snoozed). It keeps alerting until it's completed, archived or snoozed. An overdue task must never go quiet by itself: that's the missed sign-off.
- **The scan (opening screen), top to bottom:** **Pinned** (every open pinned task, whatever its dates), **Today** (deadline before the end of today, overdue included), **Tomorrow** (deadline tomorrow), **New** (created in the past 24 hours, newest first), **Reminders** (reminder already reached, and none of the above: deadline later or none). Only open tasks; each task appears in one section only, the first it qualifies for. A reminder that hasn't fired yet shows nowhere in the scan. Pinned, New and Reminders hide when empty. Each section is a native `<details>` (collapsible, open by default); the scan stays mounted while hidden so collapsed sections survive tab switches. Logic lives in `web/src/helpers/taskHelpers.ts` (`buildScan`).
- **Caught up** (`todayState`, `doneToday`): when no open task has a deadline before the end of today, pinned and snoozed ones included, the empty Today section shows a centred, bordered green panel: a check in a circle, "You're caught up." in large type, and "N done today" (tasks completed today, archived included). If Today is empty but a pinned task is due today or overdue, a quieter grey panel says "Nothing else due today" and "Check the pinned tasks above." Never say caught up over an overdue task, snoozed or pinned.
- **Print:** each scan section with tasks has a printer icon button at the right of its heading row, its right edge on the list's border (outside `<details>`, so it never toggles the section). It renders `PrintCard` for that section only (`flushSync`, then `window.print()`; `afterprint` clears it); everything else is `print:hidden`. The card is a 5 × 3 inch bordered box on a normal page, 10 lines a card, black and white: ☐, "!" for High, title, 📌, then "OVERDUE" (snoozed or not) and the time (`short()`, or "Rem 07:00" with only a reminder). No description, category, bells or tints.
- **Order:** Pinned and Today put overdue first, then by deadline; Tomorrow by deadline; Reminders oldest reminder first; no deadline sorts last. The order is a guess to check with Maverick.
- **Colour means alert state:** red = overdue, amber = reminder reached or due soon (`alertState`, open tasks only); a snoozed task has no tint. **Icons** (`shared/Icons`, `taskSignal`) back the colours up: red bell = overdue, amber bell = reminder or due soon, grey crossed-out bell = snoozed, green check = completed. They sit in a fixed slot at the start of each scan line and at the start of the table's Status cell; the bell is the snooze button. Pinned keeps the 📌 emoji (a glyph, not an alert tint). Don't use red or amber for anything else (the High tag is neutral), except in forms: errors are red, warnings (reminder moves, deadline passed, snooze ends) are amber. Violet = New only. Green = done or success (completed rows, the creation toast). In the full list, completed rows are muted green (done, good) and archived rows muted grey.
- **All tasks tab (`TaskTable`, TanStack Table v9):** every task, archived included. Pinned tasks are ordinary rows there. Search covers title, description, category, type and priority. Two filters: Status (Open, New, Alerting, Snoozed, Not started, In progress, Completed, Archived; archived wins over completed; Alerting = a bell showing now, Snoozed = a running snooze) and Deadline (Overdue, Today, Tomorrow, This week, This month, This quarter, Later, No deadline; week, month and quarter are the whole calendar period, Monday to Sunday, past days included; Later is after this quarter). No default sort: rows keep the API's order (by id). Both Clear buttons (toolbar, and "Clear search and filters") are outlined blue (`ACCENT_BUTTON`), like Clone. 10 rows per page; first click on a heading sorts ascending; search, filter and sort changes go back to page 1. The table stays mounted while hidden so its state survives tab switches. Keep it accessible: labelled fields (`htmlFor`), ARIA tabs with arrow keys, `aria-sort` on headings, live regions for counts, a visible focus ring.
- **Times are 24-hour** (`HH:mm`), with the day added when it isn't today.
- **Snooze** writes only `snoozedUntil`, the time it ends (no offset is stored). It never changes `remindAt`. A snoozed task stays where it is, untinted, with the snoozed icon. **Scan line 2** spells out only the deadline ("Due …"); the reminder (when it's the alert, or there's no deadline) and the snooze end follow as a small icon (alarm clock, crossed-out bell) and a short time (`short()`: "07:00", "Thu 07:00"), grey unless they're the alert, with screen-reader words and a tooltip. Snooze starts only from the bell's menu (`SnoozeMenu`, saves at once): 30 minutes, 1 hour, 3 hours, 6 hours, 8 hours, Tomorrow morning (07:00 next day; "This morning" before 07:00), all guesses to check with Maverick (`helpers/snooze.ts`). A snooze never runs past a deadline still ahead: it's capped there, "(deadline)". The edit dialog can only **end** a snooze (End snooze, applied on Save, `endSnooze` in the form values).
- **Moving a deadline before its reminder** shifts `remindAt` by the same amount, and the form shows the new time before saving. Don't reject the edit and don't clear the reminder.
- **Archiving** happens in the task edit form, by setting `archivedAt`; there is no separate archive action. Archived tasks **stay in the full list**, marked as archived, until filters exist to hide them. They never appear in Today and Tomorrow and never alert. The same save that archives a task must also set `pinned = false` and `snoozedUntil = null`, or the DB checks reject it. Un-archiving clears `archivedAt`.
- **New** = open and created in the past 24 hours (`isNew`), overdue or not; derived, never stored. A violet sparkles icon (`NewIcon`, an icon so High, In progress and New don't stack into three tags) sits right after the title, in the scan and in the table's Title cell; the New filter matches exactly the marked tasks. A new task triggers a green toast at the top right ("New task created: …") that fades after 5 s; toasts stack.
- **New task and clone use `TaskDialog`** (`mode`: edit, new, clone) and POST every field (`planCreate`). Clone is in the edit dialog, works on completed and archived tasks, and copies the form as on screen (unsaved edits included) without saving the original. It copies title, description, priority, category, type, dates and pinned, and resets status, completed, archived and snooze. The Clone button is outlined blue (`ACCENT_BUTTON`): a main action, but not Save. Its reminder follows the edit rule (moves only when the new deadline lands before it).
- **Clone** is a create that copies fields. Complete, snooze, pin and archive are updates. Keep the API thin: list, create, update.
- `category` and `type` are nullable plain text columns. There's no categories table, on purpose.
- The DB enforces: reminder ≤ deadline when both are set (a reminder with no deadline is valid and expected); snooze needs a deadline or a reminder; snooze > reminder; no snooze on completed or archived tasks; no pin on archived tasks. The DB deliberately does **not** enforce "in the future" or `completedAt >= createdAt`, so past work can be logged.
